# 项目方案生成器

## 0. 技能定位

本技能用于生成完整、专业、可直接用于招投标的项目方案文档。方案涵盖项目全生命周期所需的核心内容，确保文档具备商业说服力和技术可行性。

核心特点：采用多角色多Agent圆桌讨论机制，对技术方案、架构设计、预算周期等关键内容进行充分论证，确保方案的专业性和可行性。

## 1. 启用前判断

### 必须先追问的情况

出现以下任一情况时，不应直接给确定性方案，必须先追问或明确标注假设：

- 项目名称或简称不明确
- 项目类型不明确（软件/硬件/软硬结合/服务/综合）
- 客户背景或行业领域不明确
- 核心需求或目标不明确
- 预算范围或报价模式不明确
- 交付周期要求不明确

### 信息收集清单

在生成方案前，应尽量收集以下信息：

| 类别 | 必要信息 | 可选信息 |
|------|----------|----------|
| 项目基础 | 项目名称、项目类型、客户名称、所属行业 | 项目编号、投标编号 |
| 需求范围 | 核心功能需求、业务目标、成功标准 | 非功能需求、约束条件 |
| 市场背景 | 行业现状、痛点分析 | 竞品分析、市场趋势 |
| 预算报价 | 预算范围、报价模式（固定/人天/里程碑） | 成本构成明细 |
| 周期计划 | 总工期、关键里程碑 | 阶段划分、验收节点 |
| 团队配置 | 核心角色、团队规模 | 人员资质要求 |
| 技术约束 | 技术栈偏好、部署环境 | 安全要求、合规要求 |

## 2. 多角色圆桌讨论机制

### 2.1 核心理念

方案生成不是单点输出，而是多角色协作讨论的结果。每个技术决策、架构选择、预算估算都需要经过多角度审视和充分论证。

### 2.2 角色池定义

#### 默认角色（必启）

| 角色 | 职责 | 关注重点 |
|------|------|----------|
| 项目经理 | 整体把控、进度协调、风险统筹 | 可行性、资源协调、里程碑 |
| 系统架构师 | 架构设计、技术选型、技术决策 | 技术可行性、扩展性、性能 |
| 成本分析师 | 预算编制、成本核算、报价策略 | 成本合理性、利润空间 |

#### 按需角色（条件启用）

| 角色 | 启用条件 | 关注重点 |
|------|----------|----------|
| 需求分析师 | 需求复杂或有业务流程 | 需求完整性、边界清晰 |
| 前端架构师 | 有前端界面需求 | 用户体验、交互设计、前端技术栈 |
| 后端架构师 | 有后端服务需求 | 服务架构、接口设计、性能 |
| DBA | 涉及数据库设计 | 数据模型、性能优化、数据安全 |
| 安全专家 | 涉及账号、支付、隐私、合规 | 安全风险、合规要求 |
| DevOps工程师 | 涉及部署、运维 | 部署方案、运维成本、监控 |
| 测试专家 | 质量要求高或复杂系统 | 测试策略、质量保障 |
| 行业专家 | 特定行业领域项目 | 行业规范、业务特性 |
| 法务顾问 | 涉及合同、知识产权、合规 | 法律风险、条款审核 |

#### 角色启用规则

- **纯软件Web/App**：项目经理、系统架构师、成本分析师、前端架构师、后端架构师、DBA
- **后端平台/中间件**：项目经理、系统架构师、成本分析师、后端架构师、DBA、DevOps工程师
- **嵌入式/IoT**：项目经理、系统架构师、成本分析师、后端架构师、测试专家
- **涉及支付/账号**：必须启用安全专家
- **涉及云部署**：必须启用DevOps工程师
- **受监管行业**：必须启用法务顾问、安全专家

### 2.3 圆桌讨论流程

#### 阶段 0：信息校验与角色激活

1. 输出已知信息与缺失信息
2. 明确关键假设
3. 确定启用角色清单及原因
4. 判断是否需要前置澄清

#### 阶段 1：独立初步构思

每个已启用角色独立给出：

- 核心判断与建议
- 主要风险识别
- 关键假设与前提

输出格式示例：

```
【项目经理视角】
- 核心判断：项目周期紧张，建议分阶段交付
- 主要风险：需求变更风险高
- 关键假设：客户可接受MVP优先上线

【系统架构师视角】
- 核心判断：建议微服务架构，便于扩展
- 主要风险：团队微服务经验不足
- 关键假设：有容器化部署环境

【成本分析师视角】
- 核心判断：预算需增加15%缓冲
- 主要风险：人力成本波动
- 关键假设：使用中级工程师为主
```

#### 阶段 2：圆桌碰撞与方案共识

汇总各角色意见，识别：

- **冲突点**：各角色意见不一致的地方
- **Trade-off**：需要权衡取舍的决策
- **依赖关系**：角色间的依赖和制约

输出 V1 基线方案，包含：

- 技术架构基线
- 预算估算基线
- 周期规划基线
- 风险清单基线

#### 阶段 3：挑战与迭代

由项目经理主持，各角色对 V1 方案提出挑战：

- 技术可行性挑战（架构师）
- 成本合理性挑战（成本分析师）
- 进度可实现性挑战（项目经理）
- 安全合规挑战（安全专家/法务）
- 运维可行性挑战（DevOps）

迭代修正方案，直到形成可执行共识。

#### 阶段 4：方案定稿

输出最终方案，明确：

- 确认项：已达成共识的内容
- 假设项：基于假设的内容，需标注
- 待确认项：需要客户确认的内容
- 风险项：已识别风险及应对措施

### 2.4 冲突裁决优先级

角色意见冲突时，按以下优先级裁决并说明理由：

1. **安全/合规红线**：安全专家、法务顾问意见优先
2. **业务正确性**：需求分析师、行业专家意见优先
3. **技术可行性**：系统架构师意见优先
4. **成本可控性**：成本分析师意见优先
5. **进度可实现**：项目经理意见优先
6. **体验优化**：前端架构师意见优先

### 2.5 多Agent协作机制

#### 并行讨论

对于独立模块，可启动多个Agent并行讨论：

- 技术架构Agent：负责架构设计讨论
- 预算成本Agent：负责预算编制讨论
- 进度规划Agent：负责里程碑规划讨论

#### 串行依赖

对于有依赖关系的内容，按顺序讨论：

1. 需求分析 → 架构设计 → 详细设计
2. 架构设计 → 技术选型 → 成本估算
3. 进度规划 ← 成本估算 ← 资源配置

#### 讨论结果汇总

每个讨论Agent返回结构化结果：

```json
{
  "topic": "讨论主题",
  "participants": ["角色1", "角色2"],
  "consensus": "达成的共识",
  "conflicts": ["未解决的冲突"],
  "assumptions": ["关键假设"],
  "risks": ["识别的风险"],
  "recommendation": "最终建议"
}
```

## 3. 方案文档结构

### 标准方案章节

完整方案文档应包含以下章节，按需裁剪：

#### 第一章：项目概述

1. **项目背景**
   - 行业发展现状与趋势
   - 客户业务现状分析
   - 项目建设必要性

2. **项目建设目标**
   - 总体目标
   - 具体目标（可量化）
   - 预期效益

3. **项目建设范围**
   - 功能范围边界
   - 非功能要求
   - 约束条件

#### 第二章：需求分析

1. **业务需求分析**
   - 业务流程现状
   - 业务痛点分析
   - 业务需求清单

2. **功能需求分析**
   - 功能模块划分
   - 功能点清单
   - 用例描述

3. **非功能需求分析**
   - 性能需求
   - 安全需求
   - 可用性需求
   - 可扩展性需求

#### 第三章：总体设计

1. **设计原则与依据**
   - 设计原则
   - 技术标准与规范
   - 参考依据

2. **系统架构设计**
   - 总体架构图
   - 逻辑架构
   - 物理架构
   - 部署架构

3. **技术选型**
   - 技术栈选择与理由
   - 备选方案对比
   - 核心技术组件
   - 技术风险评估

#### 第四章：详细设计

1. **功能模块设计**
   - 各模块详细设计
   - 模块间接口设计
   - 数据流设计

2. **数据库设计**
   - 数据库选型
   - 数据模型设计
   - 数据安全策略

3. **接口设计**
   - 外部接口
   - 内部接口
   - API 规范

#### 第五章：项目实施计划

1. **项目周期规划**
   - 总体时间安排
   - 阶段划分
   - 关键里程碑

2. **项目组织架构**
   - 组织结构图
   - 角色职责定义
   - 沟通机制

3. **人员配置计划**
   - 团队规模
   - 人员角色分配
   - 人员资质要求

4. **工作分解结构（WBS）**
   - 任务分解
   - 工期估算
   - 依赖关系

#### 第六章：项目预算

1. **报价说明**
   - 报价依据
   - 报价范围

2. **费用明细**
   - 人力成本
   - 硬件/软件采购成本
   - 其他费用
   - 税费

3. **付款方式**
   - 付款节点
   - 付款比例
   - 付款条件

#### 第七章：质量保障

1. **质量管理体系**
   - 质量目标
   - 质量保证措施

2. **测试计划**
   - 测试策略
   - 测试类型
   - 测试环境

3. **验收标准**
   - 阶段验收标准
   - 最终验收标准

#### 第八章：风险管理

1. **风险识别**
   - 技术风险
   - 管理风险
   - 外部风险

2. **风险评估**
   - 风险等级评估
   - 风险影响分析

3. **风险应对策略**
   - 预防措施
   - 应急预案

#### 第九章：售后服务

1. **服务承诺**
   - 质保期限
   - 服务响应时间

2. **运维支持**
   - 日常运维
   - 故障处理
   - 升级服务

3. **培训计划**
   - 培训对象
   - 培训内容
   - 培训方式

#### 第十章：公司资质与案例

1. **公司简介**
   - 公司概况
   - 核心优势

2. **资质证书**
   - 企业资质
   - 行业认证

3. **成功案例**
   - 相关项目案例
   - 客户评价

### 附录

- 附件清单
- 术语表
- 参考文献

## 4. 角色与分工模板

### 标准项目角色

| 角色 | 职责 | 技能要求 | 投入比例 |
|------|------|----------|----------|
| 项目经理 | 整体协调、进度控制、风险管理 | PMP认证、5年以上经验 | 50%-100% |
| 技术总监 | 技术决策、架构设计、技术评审 | 架构师认证、8年以上经验 | 30%-50% |
| 需求分析师 | 需求调研、需求文档编写 | 业务分析能力、3年以上经验 | 50%-100% |
| 系统架构师 | 系统架构设计、技术选型 | 架构设计能力、5年以上经验 | 50%-100% |
| 前端开发工程师 | 前端界面开发、交互实现 | Vue/React、3年以上经验 | 100% |
| 后端开发工程师 | 后端服务开发、接口实现 | .NET/Java、3年以上经验 | 100% |
| 数据库工程师 | 数据库设计、性能优化 | SQL Server/MySQL、3年以上经验 | 30%-50% |
| 测试工程师 | 测试用例设计、测试执行 | 自动化测试、2年以上经验 | 50%-100% |
| 运维工程师 | 部署实施、运维支持 | Linux、3年以上经验 | 30%-50% |
| UI设计师 | 界面设计、交互设计 | 设计工具、2年以上经验 | 30%-50% |

### 角色配置原则

- 小型项目（< 3个月）：项目经理兼需求分析师，精简团队
- 中型项目（3-6个月）：完整核心团队，按需配置支持角色
- 大型项目（> 6个月）：完整团队配置，增加管理层次

## 5. 预算估算模板

### 人力成本估算

```
人力成本 = Σ(角色人天数 × 日均成本)
```

### 标准人天成本参考

| 角色 | 初级 | 中级 | 高级 |
|------|------|------|------|
| 项目经理 | 2000 | 3000 | 5000 |
| 技术总监 | 3000 | 4500 | 7000 |
| 系统架构师 | 2500 | 4000 | 6000 |
| 开发工程师 | 1500 | 2500 | 4000 |
| 测试工程师 | 1200 | 2000 | 3000 |
| 设计师 | 1500 | 2500 | 4000 |

### 其他费用类别

- 硬件采购成本
- 软件授权费用

- 差旅费用
- 培训费用

## 6. 周期估算模板

### 标准阶段划分

| 阶段 | 主要工作 | 典型占比 |
|------|----------|----------|
| 需求分析 | 需求调研、需求文档 | 10%-15% |
| 系统设计 | 概要设计、详细设计 | 15%-20% |
| 开发实现 | 编码、单元测试 | 40%-50% |
| 系统测试 | 集成测试、系统测试 | 15%-20% |
| 部署上线 | 部署、培训、验收 | 5%-10% |

### 里程碑设置原则

- 每个阶段结束设置里程碑
- 关键决策点设置里程碑
- 付款节点与里程碑对齐

## 7. 技术栈默认偏好

### 软件项目默认技术栈

- 前端：Vue 3 + TypeScript + Element Plus
- 后端：.NET Core 8 / .NET 8
- 数据库：SQL Server
- 缓存：Redis
- 消息队列：RabbitMQ（按需）

### 偏离默认栈的情况

只有在以下情况才偏离默认栈，并必须说明原因：

- 客户明确指定其他技术栈
- 与现有系统集成需要
- 特殊性能或安全要求
- 许可证或成本约束

## 8. Pandoc 检测与文档导出

### Pandoc 检测流程

1. 生成 Markdown 源文件后，自动检测 pandoc 是否可用
2. 检测命令：`pandoc --version`
3. 如果可用，自动转换为 docx 格式

### 自动安装 Pandoc

如果 pandoc 不可用，按以下顺序尝试自动安装：

- Windows：优先 `winget install --id JohnMacFarlane.Pandoc`，其次 `choco install pandoc`
- macOS：`brew install pandoc`
- Debian/Ubuntu：`sudo apt-get install pandoc`
- RHEL/CentOS/Fedora：`sudo dnf install pandoc` 或 `sudo yum install pandoc`

### 文档输出规则

- 源文件：Markdown 格式，英文文件名，存放于 `project_docs/` 目录
- 交付文件：docx 格式，中文文件名，存放于 `project_docs/交付/` 目录
- 文件命名：`{项目名称}方案.docx`
- 目录不存在时自动创建

### 交付目录附加文件

每次生成交付目录时，必须额外附带：

- 交付总封面
- 交付清单目录
- 文档阅读指南

## 9. 输出工作流

### 阶段 0：信息收集与角色激活

1. 收集项目基础信息
2. 确认缺失信息并追问
3. 明确假设条件
4. 确定启用角色清单

### 阶段 1：多角色圆桌讨论

1. 各角色独立构思
2. 圆桌碰撞与方案共识
3. 挑战与迭代
4. 方案定稿

### 阶段 2：方案框架生成

1. 确定方案章节结构
2. 生成各章节大纲
3. 确认内容深度

### 阶段 3：详细内容编写

1. 按章节顺序编写完整内容
2. 确保逻辑一致性
3. 补充图表和表格

### 阶段 4：文档输出

1. 生成 Markdown 源文件
2. 检测并安装 pandoc
3. 转换为 docx 格式
4. 生成交付目录和附加文件

## 10. 守则

- 方案内容必须具体、可执行，禁止泛泛而谈
- 所有数据必须有依据，无依据的必须标注为估算或假设
- 技术选型必须说明理由和备选方案
- 预算报价必须明细清晰，可追溯
- 周期计划必须合理，有缓冲空间
- 风险识别必须全面，应对措施必须具体
- pandoc 可用时必须生成 docx 交付文件
- 文档命名使用"{项目名称}方案"格式，不使用"招投标方案"等字眼
- 必须展示多角色讨论过程，不要只给结论
- 要有真实冲突与 Trade-off，不要一团和气
- 角色意见冲突时，按优先级裁决并说明理由
- 方案必须落地到具体技术组件、模块、接口层面
